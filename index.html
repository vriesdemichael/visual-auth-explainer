Visual auth explainer

OAuth and OpenID Connect on one living diagram, with its messages recorded from a real Keycloak. The specs are the same elsewhere, though error codes, token formats, defaults and the stored-token API are Keycloak's own. Pick a question and follow it, one message at a time. New to this? Start with the first one.

  1. Start here

    What everything else builds on, in plain words.

    1. How does an app get access? An app acts for a user, without ever seeing their password.
    2. Why not just send the token back through the browser? Why the browser only gets a code, and what happened to the way that did not.
    3. How does an app know who logged in? Access is not identity, which is what OpenID Connect adds.
    4. When does the user get asked? What a scope is, and why you may never have seen the question.
    5. How do an app and a provider get to know each other? What people have to do before anyone can log in.
    1. I have to add login to an app. What do I do? The part you do once, which part of your code is left, and what a library does.

  2. Keeping it safe

    What can go wrong, and what stops it.

    1. What is different about an app with no secret? An app in a browser or on a phone cannot keep one, so what proves who it is?
    2. What if someone steals the code? Watch them take it as it crosses the browser, and get the tokens.
    3. How does PKCE work? The app proves it started this login, with a value that was never in a redirect.
    4. What does PKCE do to the attacker? The same attempt, a different answer, and a cost that remains.
    1. Can a code be stolen from an app with a secret? They get the code, but cannot trade it. That is not the end of it.
    2. Does an app with a secret need PKCE too? Why current advice says yes, even when a stolen code is not enough alone.
    3. What does an attacker get against both? A secret and PKCE together, against the same attempt.
    1. How does DPoP stop a stolen token being used? It ties a token to a key that never leaves the app. The theft itself is not drawn.
    2. How can a proof be stopped from being used later? A nonce from the server. The spec allows it, and Keycloak did not ask.

  3. Logging in somewhere else

    When the identity provider hands the login to another one.

    1. How do you log in with another provider? The app does not notice, and that is the point.
    2. How does the app call the other provider's API? The identity provider kept its tokens, and hands them over. Advanced
    3. What changes with API V2 for stored tokens? Only the access token, and the client has to be allowed to ask. Advanced

  4. Setting up a real app

    The combinations people use, with what is really sent.

    1. A web app on a server It can keep a secret. With OpenID Connect to know who logged in, and PKCE on top. Advanced
    2. An app that runs in the browser No secret to keep, so PKCE protects the code. The tokens then live in the page, which is the harder problem. Advanced
