The app trades for on a direct call. A has no secret to prove who it is, but it does have the , which was never in a . Someone who only saw the code cannot do this. If the app runs in the browser, this call comes from its own JavaScript.

In practice. A does this. There is no secret to keep, because there could not be one. For example, passport-oauth2 once it has the code, and openid-client when you call its code grant.

Direct. One system calls another, with no redirect through the browser. Also called the back channel.

What if someone else gets hold of the code?

If all they can do is read the code, they get nothing. They would also need the verifier, which is only being sent now, and the they may have seen cannot be turned back into it. Someone who can also change the login request as it goes by can get round this, though that takes much more.

In Keycloak: Web origins

An app that runs in the page makes this request from the page, so the browser blocks it unless the app's origin is listed here. It shows up as a CORS error, and the code still works afterwards, so the login can be tried again once the origin is listed. The app in this recording is a server standing in for one, which needs nothing here.

In Keycloak: Require PKCE

Someone with only the code gets a 400 invalid_grant: PKCE code verifier not specified. That try also uses up the code, so the real app has to start the login again. That is how Keycloak does it, and the specs do not say whether a failed try counts.
