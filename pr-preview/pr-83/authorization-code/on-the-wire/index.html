Adds proof of who logged in on top of the access OAuth grants.

Client type

Whether the app can keep a secret. One that cannot, such as an app in a browser, has to rely on PKCE.

The app proves it started this login, so a stolen code is no use alone. Current advice is to have it on, and a public client must.

Someone copies the code as it crosses the browser and tries to use it. Flip PKCE or the client type to see what changes.

Token type

Whether holding the token is enough, or the app must also prove it holds a key.

The IdP hands the login to another IdP. The app does not notice.

App to IdP

POST /token

The app trades the code for tokens

The app trades for on a direct call, and proves who it is with . Someone who only saw the code in the browser cannot do this.

In practice. A does this. Keep the secret in your configuration, and out of your code. For example, passport-oauth2 once it has the code, and openid-client when you call its code grant.

Direct. One system calls another, with no redirect through the browser. Also called the back channel.

What if someone else gets hold of the code?

They cannot do this alone, because they do not have the secret. But they can hand the code to the real app from their own browser, so that it trades the code for them, and then they are in as the user. stops this as well.

In Keycloak: Client authentication

On, which makes this a confidential client. Turn it off and this request needs no secret.

Clients › your client › Settings › Capability config › Client authentication

In Keycloak: Require PKCE

Without the secret, this gets a 401, with the error unauthorized_client, where RFC 6749 says invalid_client. The code itself is still good, and PKCE is not insisted on unless this is turned on.
