Why not send the token here?

That is the implicit flow, and it is what clients in a browser used to do. The token then sits in the address, where browser history and anything running in the page can get at it, and it cannot be tied to the client that asked. Current advice is not to use it, though you will still see it offered.

Off on a new client, though the server lists it as something it supports. Asking for it then gets an error, and turning this on lets the token go through the browser. Current advice is to leave it off.

What it carries

  • code query The one-time code, which the app trades for tokens.
  • state query A random value the app checks when the user comes back, so nobody can slip an answer into this user's login. It does not stop someone starting a login in their own browser and handing the app a stolen code, which takes PKCE.
  • iss query Names the server this came from, so a client that uses more than one can tell which answered
  • Set-Cookie header The session, on the address of the authorization server
