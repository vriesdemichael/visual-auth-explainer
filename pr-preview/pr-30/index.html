Visual auth explainer

OAuth and OpenID Connect on one living diagram, checked against a real server. Pick a question and follow it, one message at a time. New to this? Start with the first one.

  1. Start here

    What everything else builds on, in plain words.

    1. How does an app get access? An app acts for a user, without ever seeing their password.
    2. How does an app know who logged in? Access is not identity, which is what OpenID Connect adds.
    3. How do an app and a provider get to know each other? What people have to do before anyone can log in.

  2. Keeping it safe

    What can go wrong, and what stops it.

    1. What if someone steals the code? An app with no secret, and a code that crosses the browser.
    2. How does PKCE stop a stolen code? The app proves it started this login, with a value that never crossed the browser.
    3. Does an app with a secret need PKCE too? Why current advice says yes, even when a stolen code is not enough alone.
    1. What if someone steals the token? DPoP ties a token to a key that never leaves the app.
    2. How can a proof be stopped from being used later? A nonce from the server. The spec allows it, and Keycloak did not ask.

  3. Logging in somewhere else

    When the identity provider hands the login to another one.

    1. How do you log in with another provider? The app does not notice, and that is the point.
    2. How does the app call the other provider's API? The identity provider kept its tokens, and hands them over. Real traffic
    3. What changes with API V2 for stored tokens? Only the access token, and the client has to be allowed to ask. Real traffic

  4. Setting up a real app

    The combinations people use, with what is really sent.

    1. A web app, set up the way it should be On a server that can keep a secret, with OpenID Connect and PKCE. Real traffic
    2. An app that runs in the browser No secret to keep, so PKCE does the work. Real traffic
